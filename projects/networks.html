Summary

Four networked apps built in Java, each one a step up from the last. The same team of four worked on all of them.

Chat app. A client-server chat with a global chat, private messages in their own tabs, a live online-users list, and clean handling of disconnects.

Reliable Blast UDP file transfer. A file-transfer app comparing plain TCP with RBUDP, where data is blasted over UDP in windows and only the lost packets are re-sent, negotiated over a separate TCP channel.

VoIP app. Call setup runs through the server over TCP, and audio then flows directly between peers over UDP. It supports one-to-one and group calls, direct and group chats, voice notes, and a live user list.

Encrypted anonymous P2P file sharing. Clients search each other's shared files through a central server, but files transfer directly between peers so users stay anonymous to each other. Transfers can be paused and resumed.

My role

Each app was a team effort, and my part shifted with it: the server and protocol for the chat app, both ends of the RBUDP protocol, the JavaFX client for VoIP, and encryption across the whole P2P system once the team had built the protocol.

Mine
  • Chat: the multi-threaded TCP server and the shared message protocol
  • RBUDP: both the sender and receiver protocol engines, protocol auto-detection, the Makefile and the backend test harness
  • VoIP: the JavaFX client, group calls, voice-note wiring, race-condition fixes, and the noise gate fix
  • P2P: encryption across the whole system, chunked encryption of large files, and the automated experiment harness
The team's
  • Chat: the client
  • RBUDP: the rest of the app and the TCP versus RBUDP experiments
  • VoIP: the server and the rest of the app, and the packet-loss, call-setup latency and stress experiments
  • P2P: the protocol itself, built before I added encryption: search through the server, direct transfers, pause and resume

What I built

Multi-client chat app

  • The multi-threaded TCP server, one thread per client.
  • The shared message protocol used by client and server.

Reliable Blast UDP file transfer

  • Both the sender and receiver protocol engines.
  • Automatic detection of which protocol is in use.
  • The Makefile and the backend test harness.

VoIP app

  • The JavaFX client (about 1,900 lines): call controls, group calls, chats, and voice-note recording and playback with a waveform visualiser.
  • Group calls and the voice-note backend wiring.
  • Fixes for race conditions in the client's networking and audio code.
  • A microphone noise gate that no longer clips speech.

Encrypted anonymous P2P file sharing

  • Encryption across the whole system:
    • RSA-2048 (OAEP) key exchange during the handshake.
    • AES-GCM session keys.
    • Encrypted control traffic between clients and server.
  • A fix for out-of-memory failures on large files, by encrypting them in separately authenticated chunks.
  • An automated experiment harness that measures transfer throughput, search latency with up to 20 clients, and file integrity across pause and resume.

Interesting problems

Encrypting a protocol that already worked

The team had built the P2P protocol before encryption was on the table. I added RSA-2048 key exchange, AES-GCM session keys and encrypted control traffic across the whole system without breaking routing through the server. Large files then ran out of memory, so I split them into separately authenticated chunks.

RBUDP lost to TCP

RBUDP blasts data over UDP in windows and re-sends only the lost packets, so on paper it should beat plain TCP. In the team's experiments, TCP was faster at every file size we tested.

Race conditions and a noise gate that ate words

The VoIP client's networking and audio code had race conditions that I tracked down and fixed. The microphone noise gate was also clipping speech, so I made it stop.
